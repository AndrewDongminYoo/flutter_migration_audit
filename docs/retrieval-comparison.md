# 검색 방식 비교: 키워드, 임베딩, 버전 필터

Flutter 3.24 → 3.27 업그레이드에서 Android 시스템 바와 관련된 질문 15개로 여섯 가지 검색 방식을 비교했습니다. 숫자 결과는 [results/retrieval/report.md](../results/retrieval/report.md)에, 질문별 상위 결과는 [results/retrieval/results.json](../results/retrieval/results.json)에 있습니다.

## 설정

- 질문: [eval/questions.jsonl](../eval/questions.jsonl)의 영어 질문 15개입니다. 개발자가 실제로 물을 법한 문장으로 썼습니다.
- 정답: 질문마다 정답 문서, 판본, 정답 문장을 정해 두었습니다. 정해진 판본의 정해진 문서에서 정답 문장이 들어 있는 섹션만 정답으로 인정합니다. 14개는 Flutter 3.27 판본이 정답이고, 1개(q13)는 3.27 이후에 고쳐진 현재 판본이 정답입니다.
- 코퍼스: 다섯 스냅샷(`flutter-3.24`, `flutter-3.27`, `flutter-3.32`, `flutter-3.35`, `latest`)의 문서를 제목 단위로 나눈 8,226개 섹션입니다. 3.27 이후 판본이 세 개라서, 3.27 판본과 비슷한 다른 판본이 그만큼 많습니다.
- 방식: BM25와 임베딩(`BAAI/bge-small-en-v1.5`)에 각각 필터를 붙이지 않은 방식, 목표 버전 스냅샷 필터(`+version`)를 붙인 방식, 문서별 버전 표기 필터(`+label`)를 붙인 방식으로 여섯 가지입니다. 재순위화는 하지 않았습니다.
- 버전 표기 필터: 문서 하단의 `Stable release`, breaking change 색인 페이지의 릴리스 구분, 하단의 `Landed in version` 순서로 처음 찾은 표기를 그 문서의 버전으로 보고, 목표 버전(3.27) 이하인 문서만 남깁니다. 스냅샷은 가리지 않습니다. 표기가 없는 문서는 거를 근거가 없으므로 남깁니다(`fma.evalset.passes_label_filter`). 전체 순위에서 걸러 낸 뒤 10위까지 자르므로, 다른 방식과 같은 후보를 놓고 비교합니다.
- 지표: 1위 적중률(hit@1), 3위 이내 적중률(hit@3), MRR@10, 그리고 1위 결과가 같은 문서의 같은 섹션이지만 판본이 다른 비율(잘못된 판본@1)입니다.

## 결과

| 방식              | hit@1 | hit@3 | MRR@10 | 잘못된 판본@1 |
| ----------------- | ----- | ----- | ------ | ------------- |
| bm25              | 0.27  | 0.40  | 0.35   | 0.13          |
| embedding         | 0.07  | 0.53  | 0.30   | 0.27          |
| bm25+version      | 0.33  | 0.53  | 0.48   | 0.07          |
| embedding+version | 0.60  | 0.67  | 0.63   | 0.07          |
| bm25+label        | 0.27  | 0.40  | 0.35   | 0.13          |
| embedding+label   | 0.07  | 0.60  | 0.32   | 0.33          |

## 해석

### 임베딩은 판본을 구분하지 못합니다

필터가 없는 임베딩 검색이 정답을 1위에 올린 질문은 15개 중 1개(q09)뿐이고, 그마저도 동점 처리 순서 덕분입니다(아래 설명). 15개 중 4개는 1위가 정답과 같은 섹션의 다른 판본이었습니다. 판본 사이의 차이는 몇 문장에 불과해서 임베딩 벡터가 거의 같아지고, 어느 판본이 1위가 될지는 사실상 우연에 맡겨집니다. 3위 이내 적중률(0.53)은 오히려 BM25(0.40)보다 높습니다. 정답 섹션 자체는 잘 찾지만, 판본을 고르지 못한다는 뜻입니다.

q09와 q12의 정답 섹션은 다른 판본과 글자까지 같습니다. 그래서 임베딩 점수도 완전히 같고, 어느 판본이 1위가 될지는 동점일 때 어떤 순서로 정렬하느냐에 따라서만 정해집니다. 처음 실행에서는 정렬 순서가 고정되어 있지 않아 두 질문 모두 다른 판본이 1위였고(hit@1 0.00, 잘못된 판본@1 0.33), 정렬을 고정한 지금은 q09만 3.27 판본이 먼저 나옵니다. 이런 경우에는 내용만 보고 판본을 구분할 방법이 없고, 스냅샷 같은 메타데이터로만 거를 수 있습니다.

버전 필터를 붙이면 임베딩의 1위 적중률은 0.07에서 0.60으로, MRR은 0.30에서 0.63으로 오릅니다. 네 방식 중 가장 좋은 결과입니다. 잘못된 판본@1은 0.27에서 0.07로 내려가는데, 남은 하나는 아래에서 설명하는 q13입니다.

BM25는 필터를 붙여도 개선 폭이 작습니다(1위 적중률 0.27 → 0.33). BM25는 판본보다 어휘 불일치 때문에 놓치는 경우가 더 많기 때문입니다.

### 문서별 버전 표기로는 판본을 거를 수 없습니다

버전 표기 필터는 스냅샷 필터를 대신하지 못합니다. BM25에서는 결과가 필터가 없을 때와 질문별 순위까지 같았고, 임베딩에서는 잘못된 판본@1이 오히려 0.27에서 0.33으로 늘었습니다.

이유는 표기가 문서의 판본이 아니라 변경이 들어간 릴리스를 가리키기 때문입니다. 정답 문서인 `default-systemuimode-edge-to-edge.md`는 3.27, 3.32, 3.35, 현재 판본 모두 `Stable release: 3.27`로 표기가 같고, 출시 전에 작성된 3.24 판본에는 표기가 없습니다. 그래서 다섯 판본이 모두 필터를 통과하고, 판본을 고르는 일은 필터가 없을 때와 똑같이 검색 점수에 맡겨집니다.

표기 필터가 걸러 낸 것은 3.27 이후 릴리스의 breaking change 문서뿐입니다. 15개 질문의 10위 안에서 BM25는 하나도 거르지 않았고, 임베딩은 3.35·3.44·3.50으로 표기된 문서 7개를 걸렀습니다. 그 결과 q02(기본 대상 SDK)는 3.35의 ABI 필터 문서가 빠져 정답이 7위에서 3위로 올랐고, q11(`SafeArea`와 `MediaQuery`)은 3위에서 2위로 올랐습니다. 하지만 q11의 1위는 표기가 없는 가이드의 3.24 판본으로 바뀌었고, 이것이 잘못된 판본으로 집계됐습니다.

표기가 없거나 서로 어긋난 문서의 영향은 다음과 같습니다.

- 표기가 없는 문서는 모두 필터를 통과합니다. 가이드 141개, 릴리스 노트 29개, API 문서 77개, 그리고 breaking change 문서 중 54개가 여기에 해당합니다. 표기 필터를 거친 10위 안의 결과 150칸 중 BM25는 79칸(53%), 임베딩은 74칸(49%)이 표기 없는 문서였습니다. API 문서와 가이드의 정답 질문(q07~q12, q15)에서는 필터가 판본을 전혀 가리지 못한다는 뜻입니다.
- 하단 표기와 색인 구분이 서로 어긋난 문서는 20개입니다(예: `buttons.md`는 하단 2.0.0, 색인 1.20). 모두 3.19 이전 변경이라 3.27 기준에서는 어느 표기를 따라도 통과하고, 15개 질문의 10위 안에 한 번도 들지 않았습니다. 이 실험에서는 결과에 영향이 없었습니다.

정리하면 문서별 버전 표기는 "이 변경이 목표 버전 이후에 들어왔는가"는 알려 주지만, "이 판본이 목표 버전 시점의 문서인가"는 알려 주지 못합니다. 판본을 고르는 데는 스냅샷 같은 수집 시점 메타데이터가 필요합니다.

### 판본이 늘어나면 필터 없는 검색이 더 나빠집니다

코퍼스에 `flutter-3.32`와 `flutter-3.35` 스냅샷을 추가하기 전에는 스냅샷이 세 개(4,864개 섹션)였습니다. 같은 질문으로 비교하면 버전 필터를 붙인 두 방식의 결과는 질문별 순위까지 하나도 바뀌지 않았습니다. 반면 필터가 없는 두 방식은 나빠졌습니다.

| 방식      | hit@3 (스냅샷 3개 → 5개) | MRR@10      | 잘못된 판본@1 |
| --------- | ------------------------ | ----------- | ------------- |
| bm25      | 0.47 → 0.40              | 0.38 → 0.35 | 0.07 → 0.13   |
| embedding | 0.60 → 0.53              | 0.33 → 0.30 | 0.27 → 0.27   |

비슷한 판본이 늘어날수록 필터 없는 검색에서는 정답 판본이 다른 판본에 밀립니다. 지원하는 업그레이드 구간을 늘릴수록 판본 필터가 더 중요해진다는 뜻입니다.

### 고친 사례: q07 `immersiveSticky`

q07은 "동영상 플레이어에서 `SystemUiMode.immersiveSticky`로 시스템 바를 숨기는데, Android 15를 대상으로 해도 동작하나요?"라는 질문입니다. 정답은 3.27 API 문서의 `SystemUiMode.immersiveSticky` 섹션이고, 이 섹션에는 "Android SDK 15(API 35) 이상을 대상으로 하면 마이그레이션해야 이 모드를 쓸 수 있다"고 적혀 있습니다.

필터가 없으면 두 방식 모두 다른 판본을 1위로 가져왔습니다.

- BM25는 3.35 판본을 1위로 가져왔습니다. 3.35부터는 "API 36 이상이면 시스템이 이 값을 무시한다"는 문장이 추가되어 있습니다. 이 판본을 근거로 쓰면 3.27 사용자에게 아직 해당하지 않는 Android 16 동작을 답하게 됩니다. 정답(3.27 판본)은 5위였습니다.
- 임베딩은 3.24 판본을 1위로 가져왔습니다. 이 판본에는 API 35 경고가 아예 없습니다. 이 판본을 근거로 쓰면 "그대로 동작한다"는 잘못된 답이 나옵니다. 둘 중 더 위험한 오답입니다.

목표 버전 스냅샷으로 필터를 걸자 두 방식 모두 3.27 판본을 1위로 가져왔습니다. CLI는 여기에 한 단계를 더 둡니다. 근거마다 필요한 판본을 정해 두고, 검색 결과가 다른 판본이면 문장이 같아도 받지 않습니다(`src/fma/evidence.py`).

### 필터가 정답을 막는 경우: q13 다크 모드

q13은 "opt-out 속성을 넣었는데 다크 모드에서는 여전히 edge-to-edge로 보인다"는 질문입니다. 다크 모드 스타일(`values-night`)에도 같은 속성을 넣으라는 안내는 3.27 판본에는 없고, 2025년 8월에 추가됐습니다. 그래서 목표 버전 필터를 붙인 두 방식은 정답을 찾을 수 없고, 같은 섹션의 3.27 판본을 1위로 가져옵니다. 3.32와 3.35 판본에도 다크 모드 안내가 있지만 정답 문장과 표현이 달라 정답으로 치지 않습니다. 필터가 없는 BM25는 3.32 판본을 1위로 가져왔고, 정답(현재 판본)은 3위였습니다.

버전 필터만으로는 "이후에 고쳐진 누락"을 다룰 수 없다는 뜻입니다. CLI는 이 근거에만 이후 판본을 허용하는 정책을 따로 두고, 출력에 "목표 버전 이후에 고쳐진 내용"이라고 표시합니다.

### 필터로도 해결되지 않는 실패

네 방식 모두에서 성적이 나쁜 질문은 판본보다 검색 자체의 한계를 보여 줍니다.

- q01 ("업그레이드 후 앱이 상태바 뒤로 그려지는데 왜 그런가요?"): 증상을 묘사한 질문이라 `AppBar`, `SafeArea`처럼 증상과 관련된 문서가 위로 올라오고, 원인을 설명하는 breaking change 문서의 Context 섹션은 네 방식 모두에서 10위 안에 들지 못했습니다.
- q05 ("opt-out이 영구적인 해결책인가요?"): 질문은 "permanent"라고 묻고 문서는 "temporary"라고 답합니다. 어휘가 겹치지 않아 BM25는 필터를 붙여야 겨우 5위에 정답을 올렸고, 임베딩은 필터 여부와 관계없이 10위 안에 정답을 올리지 못했습니다.
- q15 ("opt-out하지 않으면 어떤 `SystemUiMode` 값이 동작하지 않나요?"): 답은 API 문서의 `SystemUiMode` 클래스 설명에 있지만, 두 방식 모두 breaking change 문서를 1위로 가져왔습니다. 그 문서는 관련은 있지만 어떤 모드가 해당하는지는 적혀 있지 않습니다.

CLI가 질문을 자유롭게 검색하지 않고, 앱에서 찾은 단서로 판단 규칙을 고른 뒤 규칙마다 정해 둔 근거 문장을 검증하는 방식을 택한 이유가 여기에 있습니다. 검색은 후보를 내고, 판단에 쓸 근거인지는 판본과 문장으로 확인합니다.

## 한계

- 질문이 15개뿐이라 방식 사이의 작은 차이(예: BM25 필터 전후 0.27과 0.33의 차이, 한 질문 분량)는 의미를 두기 어렵습니다.
- 질문과 정답을 같은 사람이 썼습니다. 질문 문장이 정답 문서의 어휘에 가까워졌을 가능성이 있습니다.
- 질문은 영어입니다. 한국어로 묻는 경우는 다루지 않았습니다.
- 임베딩 모델은 작은 영어 모델 하나만 썼고, 섹션은 2,500자에서 잘라 임베딩했습니다.
- 섹션 단위로 나눴기 때문에 정답 문장이 긴 섹션 안에 있으면 점수가 불리해질 수 있습니다.

## 재현

```sh
uv run scripts/compare_retrieval.py
```

처음 실행하면 8,226개 섹션을 임베딩합니다. 이 작업은 노트북 CPU에서 822초(스레드 6개, 다른 작업과 함께 실행해 1분 부하 평균 6~12)가 걸렸습니다. 결과는 `data/index/`에 캐시되고, 그다음부터는 몇 초 안에 끝납니다. BM25 결과는 `tests/test_evalset.py`가 매번 다시 계산해서 커밋된 결과와 비교합니다.
